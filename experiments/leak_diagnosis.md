# 1차 시도 진단 — "mAP 0.995인데 왜 실패인가"

측정일 2026-08-15 · 대상 `experiments/legacy_runs/` 19개 run + 로컬 데이터셋 8종

재현: `python3 scripts/collect_runs.py`, `python3 scripts/check_leakage.py <데이터셋 경로>`

---

## 요약

1차 시도는 19회 학습에서 mAP50 0.54~0.995를 기록했다. 대부분이 0.99대였음에도 실제 영상에 적용하면 성능이 나오지 않았다. 원인은 세 가지이며, **모두 모델이 아니라 데이터에 있다.**

| # | 원인 | 근거 |
|---|---|---|
| 1 | 학습 데이터의 **36~72%가 Gemini 생성 합성 이미지** | 아래 표 |
| 2 | val 세트가 **원본 9~16장** | 아래 표 |
| 3 | 실사 프레임의 **출처 영상이 1개** | 원본 영상 `battery_source.mp4` 단일 |

> **처음 세운 가설(train/val 누수)은 틀렸다.** base 이름 기준으로 검사한 결과 같은 원본이 train과 val 양쪽에 들어간 사례는 **0건**이다. Roboflow 분할 자체는 깨끗했다. 문제는 분할이 아니라 **분할되는 데이터의 성질**이었다.

---

## 근거 1 — 합성 이미지 비중

`Gemini_Generated_Image_*` 파일명으로 식별. `battery_vision2/README.md` 의 기술 스택에도 "이미지 증강: Gemini (합성 학습 데이터 생성)"으로 명시돼 있다.

| 데이터셋 | train | valid | 합성 비중 |
|---|---|---|---:|
| `Battery vision.slitting.yolov8` | 60장 / 20원본 | 5장 / 5원본 | **72%** |
| `battery-process-detection.v7i` | — | 10장 / 10원본 | **70%** |
| `Battery vision.coating.yolov8` | 114장 / 38원본 | 9장 / 9원본 | **60%** |
| `Battery vision.v4i.yolov8` | 195장 / 65원본 | 16장 / 16원본 | **57%** |
| `Battery vision.v7i.yolov8` | 159장 / 53원본 | 13장 / 13원본 | 50% |
| `Battery vision.v6i.yolov8` | 147장 / 49원본 | 12장 / 12원본 | 46% |
| `Battery vision.v9i.yolov8` | 126장 / 42원본 | 10장 / 10원본 | 42% |
| `Battery vision.v12i.yolov8` | 105장 / 35원본 | 9장 / 9원본 | 36% |
| `v15_raw` (9클래스) | 408장 / 136원본 | 0장 | 16% |

**시각적으로 확인한 결과 (`experiments/viz/gt_synthetic.jpg`).** 이 이미지들은 완전한 창작물이 아니라 **실사 프레임을 조건으로 한 image-to-image 생성물**로 보인다. 근거는 세 가지다.

- 원본 영상의 `Miracle Process` 워터마크가 그대로 남아 있다
- 우하단에 Gemini 생성 이미지 표식(✦)이 찍혀 있다
- 구도와 설비 배치가 실사 프레임과 대응된다

따라서 "가짜 공장 사진"은 아니다. 그러나 **실사 프레임보다 눈에 띄게 깨끗하고 균일하게 조명돼 있다.** 실사(`gt_real.jpg`)는 어둡고 모션블러가 심하며 프레임 절반이 판독하기 어려운 반면, 생성본은 선명하고 대비가 고르다.

**해석.** train과 val이 모두 이 "정돈된" 이미지로 채워지면 모델은 쉬운 문제를 풀게 된다. 실제 영상 프레임은 조명·모션블러·occlusion이 전혀 다르므로 성능이 무너진다.

**즉 mAP 0.995는 거짓말이 아니라, 더 쉬운 문제를 푼 정답이다.**

## 근거 2 — val 세트 크기

val 원본이 9~16장이다. 클래스가 3개면 클래스당 3~5장으로 채점한 셈이다. 이 크기에서 mAP 0.995와 0.90의 차이는 이미지 한 장 차이로 뒤집힌다. **지표로 쓸 수 없다.**

`v15_raw`(RunPod 학습에 쓰인 9클래스 데이터셋)는 아예 **val이 0장**이다 (Roboflow 100% train 분할). 그럼에도 `experiments/runpod_v12/results.csv` 에는 val mAP 0.993이 기록돼 있다 → 학습 데이터로 채점한 값이다.

## 근거 3 — 실사 프레임의 단일 출처

실사 프레임은 전부 `battery_source.mp4` 한 개에서 나왔다. 같은 영상 프레임은 어떻게 분할해도 카메라·조명·설비가 동일하다. **"미학습 영상 성능"을 측정할 방법이 원리적으로 없었다.**

## 학습 이력에서 관찰되는 패턴

`experiments/history.csv` 전체 19건 중 발췌:

| run | 데이터셋 | mAP50 | mAP50-95 | imgsz |
|---|---|---:|---:|---:|
| battery_v4-2 | v16i (Colab) | 0.995 | 0.946 | 640 |
| coating_v2~v5 | coating 계열 (합성 60%) | 0.995 | 0.638~0.671 | 512 |
| slitting_v1~v3-2 | v1i~v3i (합성 72%) | 0.995 | 0.593~0.613 | 512 |
| battery_v3-4 | v15i (Colab) | 0.692 | 0.461 | 640 |
| battery_v3-2 | v13i (Colab) | 0.661 | 0.379 | 640 |
| battery_v3-3 | v14i (Colab) | 0.542 | 0.317 | 640 |

합성 비중이 높은 데이터셋일수록 mAP50이 0.995에 붙는다. 반대로 `battery_v3` 계열(v13i~v15i)만 0.54~0.69로 떨어지는데, 이들은 Colab에서 학습돼 로컬에 데이터셋이 없어 합성 비중을 직접 확인하지 못했다. **다만 `v15_raw`(v15i의 Roboflow 재수출본)의 합성 비중이 16%로 급감한 것을 보면, v13i~v15i 시점에 실사 프레임 비중을 크게 늘렸을 가능성이 높다.**

그렇다면 **0.54~0.69가 이 프로젝트의 진짜 성적**이고, 0.995는 합성 데이터가 만든 착시다.

### 남은 확인 사항

- v13i~v16i 데이터셋을 Colab Drive에서 회수해 합성 비중을 직접 측정하면 위 가설이 확정된다
- 회수가 어려우면 Phase 1에서 `v15_raw`(합성 16%)를 영상 단위로 재분할해 측정하는 것으로 대체한다

## 근거 4 — 박스 기하: 탐지 문제가 아니라 장면 분류에 가깝다

`python3 scripts/analyze_dataset.py --data data/dataset/v15_raw` 결과 (408장 / 1,326 인스턴스):

| 항목 | 값 | 함의 |
|---|---|---|
| 박스 면적 비율 중앙값 | **0.240** (이미지의 24%) | 객체가 아주 크다 |
| 5% 미만 소형 박스 | 68개 (**5%**) | 소형 객체 문제가 **없다** |
| 1% 미만 초소형 | 24개 (2%) | 〃 |
| 이미지당 박스 | 평균 3.2개 / 최대 15개 | 박스 3개면 이미지의 70%가 덮인다 |
| IoU 0.5 초과 박스쌍 | **582쌍** | 중첩이 심하다 |
| 종횡비 중앙값 | 전 클래스 0.85~1.29 | 전부 정사각형에 가깝다 |

**이 수치들이 PLAN.md의 전제 두 가지를 무효화한다.**

1. **`imgsz=1280` 과 SAHI 타일링은 근거가 없다.** 둘 다 "설비 부품이 20~30px로 축소돼 특징이 소실된다"는 가정에서 나왔는데, 실제 박스는 이미지의 24%다. 512에서도 충분히 크다. 기존 run 들이 512~640으로 학습한 것은 합리적인 선택이었다.

2. **`Separator` 를 "얇은 필름이라 박스 부적합"으로 제외한 판단은 라벨 데이터로 지지되지 않는다.** 종횡비 중앙값이 1.26으로 정사각형에 가깝다. 얇게 라벨링된 게 아니라 필름이 지나가는 **영역을 뭉뚱그려** 박스를 친 것이다.

**대신 진짜 문제가 드러난다.** 박스가 이미지의 24%를 차지하고 서로 582쌍이나 겹친다면, 이 라벨은 "여기에 이 설비가 있다"는 **장면 태그에 가깝고 위치 정보가 희박하다.** 탐지기가 배울 국소적 시각 패턴이 약하다는 뜻이며, 이는 합성 이미지 문제와 별개로 성능을 제한한다.

## 근거 5 — 라벨을 그려보니: 박스의 35%가 이미지 밖에 있다

`scripts/visualize_labels.py` 로 정답 박스를 그리고(`experiments/viz/gt_real.jpg`),
`scripts/check_boxes.py` 로 이상을 셌다.

| 이상 유형 | 개수 | 비중 |
|---|---:|---:|
| **경계 이탈** (정규화 좌표가 [0,1] 밖) | **469 / 1,326** | **35.4%** |
| 중복 박스쌍 (같은 클래스, IoU > 0.7) | 72 | 5.4% |
| 극단 종횡비 (4:1 초과) | 72 | 5.4% |
| 거대 박스 (이미지의 60% 이상) | 25 | 1.9% |

경계 이탈은 **408장 중 264장(65%)** 에 영향을 준다. 클래스별로는 `Electrode_Foil` 151개, `Press_Roller` 88개, `Numbered_Core` 84개 순이다.

**원인.** 시각화를 보면 프레임이 검은 레터박스로 둘러싸여 있는데(16:9 영상을 정사각형에 맞춘 흔적), 박스가 그 패딩 영역까지 뻗어 있다. **증강 파이프라인에서 회전·이동 후 박스를 이미지 경계로 클리핑하지 않았다.** 학습 시 ultralytics 가 일부를 보정하더라도, 라벨의 3분의 1이 실제 대상과 어긋난 좌표를 갖고 있다는 사실은 남는다.

**이건 앞의 세 원인과 성격이 다르다 — 데이터 수집 전략의 문제가 아니라 명백한 버그이고, 고칠 수 있다.**

### 그 결과가 모델에 그대로 나타난다

`experiments/viz/pred_unlabeled.jpg` — 미라벨 실사 프레임 12장에 `models/runpod_v12_best.pt` 를 돌린 결과, **거의 모든 프레임에서 화면 대부분을 덮는 큰 박스 한두 개만 예측한다.** 설비를 국소화하지 않고 "여기 기계가 있다"를 표시하는 수준이다.

이는 학습 라벨의 기하가 그대로 학습된 결과다. **탐지기가 지금 하고 있는 일은 사실상 장면 분류이며, 그렇다면 Phase 4의 "탐지 결과로 공정 구간을 특정한다"는 설계가 성립하지 않는다.**

## 이번 재설계에 반영할 것

| 진단 | 대응 |
|---|---|
| 합성 이미지 의존 | **Gemini 생성 이미지를 학습 데이터에서 전면 배제.** 실사 프레임만 사용 |
| val 세트 과소 | val 원본 100장 이상 확보. 그 전까지의 mAP는 참고치로만 표기 |
| 단일 출처 영상 | 영상 3~5개로 확장, **train·val·test를 영상 단위로 분할** |
| 측정 신뢰성 | `build_splits.py` 에 분할 간 교집합 0 을 `assert` 로 박아넣는다 |
| **박스 35%가 경계 이탈** | **재라벨링 필요.** 실사 프레임 1,055장 기준으로 다시 그린다 |
| 박스가 과대·중첩 | 라벨 기준을 "설비가 있는 영역" → "설비 자체의 윤곽"으로 좁힌다 |
| ~~소형 객체~~ | **해당 없음.** `imgsz=1280`·SAHI 계획을 철회하고 640 유지 |
| 중첩 박스 | Soft-NMS 는 유지 검토 (IoU 0.5 초과 582쌍) |

## 결론 — 원인의 우선순위

| 순위 | 원인 | 성격 | 대응 비용 |
|---|---|---|---|
| 1 | 라벨 박스 35% 경계 이탈 + 과대·중복 | **버그** | 재라벨링 (큼) |
| 2 | 실사 프레임 출처 영상 1개 | 설계 | 영상 추가 (중간) |
| 3 | val 세트 원본 9~16장 | 설계 | 분할 재구성 (작음) |
| 4 | 학습 데이터의 36~72%가 생성 이미지 | 설계 | 배제 (작음) |

**1번을 고치지 않으면 2~4번을 고쳐도 의미가 없다.** 라벨이 설비 윤곽을 가리키지 않는 한, 데이터를 아무리 늘려도 탐지기는 계속 화면 전체에 큰 박스를 그린다.

> `data/frames/v1_unlabeled/` 에 실사 프레임 1,055장이 이미 정리돼 있다. 합성 이미지를 버려도 실사 데이터는 오히려 기존 학습에 쓰인 것보다 많다.
